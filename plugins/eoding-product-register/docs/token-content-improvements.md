# 0.5.1: 등록 응답과 콘텐츠 개선

## 확인한 문제

- MCP의 긴 JSON, 제출한 원문의 재반환, 변화 없는 상태 조회가 반복해서 AI 입력에 들어갔다.
- `product_import_get`은 기본 전체 응답이었고 상품 예시도 스키마 조회마다 반환했다.
- 콘텐츠 작성 지침은 짧은 소개를 유도했다. 보존된 이전 FIT 초안에서 관광지 7개의 설명은 평균 43.3자, 모두 한 줄이었다.
- 이전 패키지 기록 한 건의 사용자 대기 제외 시간은 약 19분이지만 런타임 실행 구간은 약 2분 10초였다. 나머지는 자료 준비·AI·도구·오류가 섞인 시간으로, AI 시간만으로 단정할 수 없다.

이 기록은 2026-10-14·15의 과거 작업 두 건이며 0.5.1의 운영 성능이나 실제 토큰 사용량 측정이 아니다.

## 적용한 개선

1. JSON 들여쓰기 제거, 기본 compact 진행 응답.
2. `revision`을 받아 `afterRevision`과 `waitMs`(최대 30초)로 다음 변경을 기다린다. 변화가 없으면 작은 응답만 반환한다. 하위 FIT·콘텐츠 작업이 실행 중이면 그 상태를 유지한다.
3. 사용자가 이미 제공한 텍스트 및 보충 원문은 기본 응답에서 되돌려주지 않는다. 원문과 근거 digest는 보관하며 `includeSource:true`로 읽을 수 있다.
4. 상품 예시는 `product_import_schema({includeExample:true})`에서만 반환한다. 스키마의 reference 본문을 중복해서 읽지 않도록 스킬을 수정했다.
5. `descriptionSections`로 설명을 한 번에 작성한다. 원문에 있는 소개·특징·볼거리·이용 안내를 보존하고 진행 안내에서 본문을 다시 출력하지 않는다. 확인되지 않은 사실이나 반복 문구로 분량을 채우지 않는다.
6. 설명은 하나의 문자열로 합쳐 보관하며, 클라이언트 상한은 12,000자다. 서버의 길이 지원을 보장하지 않으며 자동 자르기는 하지 않는다. 짧은 설명 신호는 안내이며 등록을 막지 않는다.
7. 같은 종류·이름 검색을 공유하고 도시 조회와 콘텐츠 조회를 최대 4개 슬롯에서 처리한다.
8. 신규 저장한 설명 전체를 독립 재조회해 잘림을 감지한다. 기존 콘텐츠는 재사용하되 임의 수정하지 않는다.

계정·회사·검토 바인딩·단일 실행·중복 방지·저장 후 독립 재조회는 유지한다. 저장 여부가 불명확한 작업은 자동 재생성하지 않는다.

## 모의 측정

같은 입력을 기존 반환 형식과 개선된 형식으로 비교한 격리 검사 결과다. **문자수는 실제 토큰 수와 다르다.**

| 응답 | 이전 문자수 | 개선 문자수 | 감소 |
| --- | ---: | ---: | ---: |
| 기본 상품 스키마 | 10,241 | 6,857 | 33% |
| 변화 없는 실행 상태 | 773 | 180 | 77% |
| 이미 제출한 긴 원문 확인 응답 | 66,274 | 906 | 99% |

콘텐츠 조회는 요청당 20ms 지연을 둔 fixture를 각 3회 측정했다. 도시 4개·공통 이름 3개에서 GET은 20→11회, 중앙값은 156→93ms였다. 도시 1개·이름 12개에서는 GET 14회가 유지됐고 중앙값은 154→126ms였다. 전체 상품 등록 시간이나 실제 ERP 응답시간의 감소율이 아니다.

Windows 로컬 전체 회귀검사 371개와 최종 안내문을 반영한 MCP·응답 축소 검사 5개가 모두 통과했다. 실제 ERP 저장은 실행하지 않았다.

## 운영에서 확인할 항목

동일 규모 상품의 원문 수집 시작→최종 재조회 총시간, AI 호출 수, 실제 입력·출력 토큰, 준비/검토/실행 시간과 콘텐츠 누락 여부를 비교해야 한다. 완료·실패한 FIT 작업의 최상위 시간 집계가 하위 작업 종료와 다르게 보이는 기존 문제는 이번 응답 개선과 별도로 남아 있다.
